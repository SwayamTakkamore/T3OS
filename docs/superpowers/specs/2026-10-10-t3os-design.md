## 1. Overview

**T3OS** is a native Linux terminal/desktop **agent-harness control surface** for
open-weight models — the open-source analogue of [T3 Code](https://t3.codes), but
it runs its **own** agent loop against models hosted on **HuggingFace** or run
**locally**. **Gemma** is the first-class default model family.

Where T3 Code drives agent CLIs that are already installed (Claude Code, Codex,
Cursor, …), T3OS *is* the harness: it owns the model connection, the tool loop,
the permission model, and the session log.

### Primary goals (v1)

1. **Real coding agent loop** — model ↔ tools (`read_file`, `write_file`,
   `edit_file`, `list_dir`/`glob`, `grep`, `run_shell`) with streaming output.
2. **Provider layer** — two backends: **HuggingFace Inference API** (hosted, HTTP)
   and **local inference** (`@huggingface/transformers` / llama.cpp GGUF), with
   Gemma-first presets.
3. **Session / thread management** — multiple conversations, persisted history,
   resume and fork.
4. **Polished TUI** (Ink/React) — streaming tokens, inline diffs, tool-call cards,
   keyboard-driven.
5. **MCP client** — attach external MCP servers as additional tool sources.
6. **Permission modes** — ask-before-write/run vs auto-accept, behind a clear
   policy seam.
7. **Config + secrets** — model selection, HF token, per-project settings.

### Non-goals (explicitly out of scope for v1)

- No web app, no mobile app, no remote-access service.
- No proprietary provider CLIs — T3OS *is* the harness.
- No full desktop GUI in v1. The desktop is a **thin Tauri shell** reusing the
  same core; a full GUI and multi-workspace/worktrees are deferred to v2.
- Not a fine-tuning tool, not a model registry, not a cloud service.
- Explicitly **not** Ollama — HuggingFace is the model source.

### Success criteria (v1 “done”)

- `t3os` launches the TUI on Linux.
- It can be pointed at Gemma via an HF token **or** a local GGUF.
- It edits real files in a repo with visible diffs.
- A permission prompt gates writes / shell execution.
- Sessions persist and resume.
- At least one external MCP server's tools appear and are callable.
- `t3os serve` starts and the Tauri shell talks to it.

### Target user

A Linux developer who wants a local-first, open, hackable agent harness and
refuses to send code to a closed provider or run a browser.

## 2. Architecture & Components

### 2.1 Monorepo layout

pnpm workspaces, TypeScript end-to-end:

```
t3os/
  packages/
    core/      engine, zero UI deps, unit-testable
    cli/       `t3os` binary — wires core → TUI (in-process) or boots server
    tui/       Ink/React terminal UI
    server/    HTTP + WebSocket transport exposing core (`t3os serve`)
    desktop/   Tauri thin shell (v1 thin)
  docs/superpowers/specs/
```

### 2.2 Architecture: in-process core + optional server (Approach C)

`packages/core` is the engine. The TUI runs it **in-process** by default
(zero-config `t3os`). The **same** core can boot an HTTP + WebSocket server
(`t3os serve`) that the Tauri desktop — and future web/remote clients — consume.

- Rejected **A** (in-process only / embedded): simplest, but not remote-ready.
- Rejected **B** (always-on local daemon + thin clients): most faithful to T3,
  but an extra process and a harder first run.

Approach C puts the T3-like control-surface seam only where it pays off
(desktop/remote), keeps the everyday TUI dead simple, and keeps `core`
independently unit-testable.

### 2.3 `packages/core` internals

- **`provider/`** — `Provider` interface:
  `streamChat(messages, tools, opts) -> AsyncIterable<Delta>` plus
  `capabilities()` (tool-calling, streaming, context length).
  - `HuggingFaceProvider` — Inference API, OpenAI-compatible chat-completions
    endpoint, HF token.
  - `LocalProvider` — `@huggingface/transformers` for GGUF/ONNX, optional
    llama.cpp sidecar.
- **`presets/`** — maps Gemma model ids → sane defaults (chat template, context
  window, token limits). Gemma-first, but any HF model id works.
- **`agent/`** — the loop: assemble messages + tool schemas → stream from
  provider → parse tool calls → execute → feed results back → repeat.
  Includes dev.to-informed safeguards: **deterministic-first routing** (never
  call the model for pure file reads/globs), **explicit tool-call state
  boundaries**, and **loop detection** (repeated-identical-call detection, not
  just a turn cap).
- **`tools/`** — `read_file`, `write_file`, `edit_file` (exact string replace +
  diff), `list_dir`/`glob`, `grep`, `run_shell` (timeout + cwd). Each tool is
  `{ name, schema, needsPermission, run(args, ctx) }`.
- **`permissions/`** — `Policy` seam with modes `ask` | `auto-accept` |
  `read-only`. Every call is classified (`read` | `write` | `execute`) →
  auto-allow / auto-deny / pending-prompt via a callback; TUI/desktop/server each
  supply their own prompt handler.
- **`sessions/`** — `SessionStore` (JSONL under
  `~/.local/share/t3os/sessions/`): `create` / `list` / `append` / `resume` /
  `fork` (branch history at any point). Append-only event log, replayable.
- **`mcp/`** — MCP client: spawn/connect external servers (stdio + SSE/HTTP),
  `listTools()`, adapt tools into the same `Tool` interface so they flow through
  the same agent + permissions pipeline.
- **`config/`** — layered config (global `~/.config/t3os/config.json` +
  per-project `.t3os/`), model selection, permission mode, secrets via an
  `HF_TOKEN`-aware resolver (env → config → OS keyring). Never logs secrets.

### 2.4 Other packages

- **`packages/cli`** — `t3os` = in-process core → Ink TUI. `t3os serve` = same
  core → `packages/server`. Helpers: `t3os auth`, `t3os models`.
- **`packages/tui`** — Ink/React with streaming, inline diffs, tool-call cards,
  permission prompts, session picker/resume, `/` commands; depends only on core
  public types.
- **`packages/server`** — thin transport adapter exposing core over HTTP + WS
  with the **identical** API the in-process TUI uses (no second implementation,
  behavior cannot drift).
- **`packages/desktop`** — Tauri thin shell connecting to `t3os serve` (or
  auto-spawns it), renders chat/diffs/permissions. Full native GUI is v2.

**Net:** every layer above core is swappable transport/UI; core is testable
headlessly (mock `Provider`, real temp-dir `SessionStore`, real tools); TUI and
desktop provably run the same engine.

## 3. Data Flow & The Agent Loop

### 3.1 Core turn cycle

One user message → final answer. Lives in `packages/core/agent/`, pure TS, no UI
imports.

1. User input → `SessionStore.append({ type: "user_message" })`.
2. `AgentTurn.run(session, input)`:
   1. Build context = system prompt (+ project rules) + session history
      (replayed) + tool schemas (built-in + MCP).
   2. `provider.streamChat(...)` emits text deltas → emit `text`; tool calls →
      `pending[]`.
   3. For each pending tool call:
      a. `permissions.check(call)` → allow = execute / deny = `tool_result(err)`
         / ask = `await prompt()`.
      b. `tool.run(args, ctx)`.
      c. emit `tool_result`.
      d. loop-guard check.
   4. Append results to context.
   5. If any tool calls were made, go to step 2; else the turn is complete.

Every step also `SessionStore.append(event)` and `emit(delta)` to listeners.

### 3.2 Streaming contract

The provider yields typed deltas: `text`, `tool_call_start`, `tool_call_delta`
(incremental arg JSON), `tool_call_end`, `usage`, `done`. The agent consumes them
and re-emits a normalized **`AgentEvent`** stream to subscribers. This is the
**single** place the UI boundary is crossed: the TUI renders `AgentEvent`s, the
server serializes the same `AgentEvent`s over WebSocket, and the Tauri shell
consumes them. One event vocabulary, three consumers.

### 3.3 Event log = source of truth

Every `AgentEvent` and user input is appended to the session's JSONL. In-memory
turn state is *derived* from replaying the log, so "resume" and "fork" are just
"replay from offset N (optionally into a new file)". No hidden state, no DB; the
session file is human-readable and portable.

### 3.4 Deterministic-first routing (dev.to-informed)

Pure lookups — reading a file the user named, listing a directory, globbing a
pattern — are executed **by the harness** and handed to the model as context,
instead of round-tripping through inference to ask the model to call `read_file`.
The model is consulted only when there is a decision to make ("don't pay an LLM
to run a for-loop").

### 3.5 Loop detection (dev.to-informed)

Beyond a max-turn cap, the agent hashes `(tool_name, normalized_args)` per turn;
**N identical calls in a row** short-circuits with a `loop_detected` event rather
than spinning. Distinguishing repeated-identical from legitimately-iterative is
the whole trick.

### 3.6 Cancellation & partial output

A turn is an `AbortController`-scoped async routine. Ctrl-C (TUI) / `cancel` RPC
(server) aborts the in-flight provider stream and tool exec. Whatever streamed so
far is already in the log, so a cancelled turn leaves a resumable, honest record.

### 3.7 Error model

Provider errors (auth, rate limit, context overflow, network) and tool errors are
**events, not exceptions** — appended and shown inline. Tool errors are also fed
back to the model so it can self-correct. Only a truly unrecoverable boot error
throws.

## 4. Config & Secrets

### 4.1 Layered config, later wins

Resolution order for any setting:

1. Built-in defaults
2. Global user config `~/.config/t3os/config.json`
3. Project config `<repo>/.t3os/config.json` (committable; **no secrets**)
4. Environment variables (`T3OS_*`, `HF_TOKEN`)
5. CLI flags (highest)

A single `ConfigLoader` in `core/config/` merges these into one immutable
`ResolvedConfig`. Every component reads config through this object only — no
component does its own `process.env` lookups — so precedence is testable in
isolation.

### 4.2 Configurable (v1)

Default model id + provider (`hf` | `local`); per-model presets; permission mode
(`ask` | `auto-accept` | `read-only`); tool allow/deny overrides; MCP server
list; session storage dir; max-turn / loop-detection thresholds; UI theme (TUI).

### 4.3 Secrets

Only one required secret in v1: `HF_TOKEN`. Resolved via a `SecretResolver`
chain: OS keyring first (`secret-tool` on Linux, behind a tiny abstraction so it
is mockable in tests) → env var → config file (discouraged, warned). Secrets are
held in a `SecretRef` handle; the raw value is fetched only at the point of an
HTTP call and is **never** written to the session log, config dumps, or error
messages. `t3os auth` runs interactive token entry and writes straight to the
keyring.

### 4.4 Project config is commit-safe

Model choice, permission mode, MCP server names — but `.t3os/` is added to a
default deny-list for the file tools so the agent cannot rewrite its own
permissions. This mirrors T3's `project-settings` and closes a self-escalation
hole.

## 5. Permission UX & Safety

### 5.1 Mode model (three modes, one seam)

- **`ask`** (default): every `write`/`execute` tool call pauses for a prompt.
- **`auto-accept`**: writes and shell run unprompted (still logged).
- **`read-only`**: all `write`/`execute` denied outright, returned to the model
  as tool errors.

Mode is set in config, overridable per-session, and shown persistently in the TUI
status line.

### 5.2 Tool classification

Each tool declares a class:

- `read` — `read_file`, `list_dir`, `glob`, `grep` (always auto-allowed)
- `write` — `write_file`, `edit_file`
- `execute` — `run_shell`, mutating MCP servers

MCP tools default to `execute` unless the server declares otherwise, so an
unknown MCP server cannot silently get write access.

### 5.3 Prompt experience

The TUI renders an inline card: tool name, precise diff (writes) or exact command
+ cwd + timeout (shell), plus a one-line model rationale. Choices:

- **Allow once**
- **Allow for session** (tool + args-shape)
- **Always allow** (persisted to project config)
- **Deny** (optional note fed back to the model)

Denial is a normal tool result — the agent adapts, it does not crash.

### 5.4 Override & escape hatches

- Session-level mode toggle (TUI keybinding / server RPC).
- `--yolo` flag maps to `auto-accept` for one run.
- A hard **deny-list** (`.t3os/`, `.git/`, `~/.ssh`) is enforced *before* the
  policy is consulted and always wins, even in `auto-accept`.

### 5.5 Same policy, every surface

`Policy` lives in `core/`; the TUI, server, and Tauri shell supply different
prompt handlers but identical classification / deny-list / mode logic — behavior
cannot drift, and policy is unit-testable with a fake prompt handler.

### 5.6 Auditability

Every decision (allow/deny/ask-choice) is a session-log event with tool, args
hash, and mode, so a resumed session shows what was permitted and why.

## 6. Testing Strategy

### 6.1 Test pyramid, headless-first

Because `packages/core` has zero UI dependencies, the bulk of the suite is fast,
deterministic Node tests against `core` with a **mock `Provider`** that yields
scripted deltas (text, tool calls, errors). No network, no model, no GPU in unit
tests.

### 6.2 Layers

1. **`core` unit tests** (Vitest):
   - provider stream parsers (feed recorded SSE/JSON fixtures from HF and local)
   - the agent loop (multi-turn tool-calling, loop detection, cancellation via
     `AbortController`, error-as-event)
   - each tool against a real temp dir
   - `Policy` with a fake prompt handler across all three modes + deny-list
   - `SessionStore` append/replay/fork round-trips
   - `ConfigLoader` precedence
   - `SecretResolver` (keyring mocked)
2. **Golden/contract tests**: recorded provider transcripts replayed to assert
   the emitted `AgentEvent` sequence — guards the event vocabulary that
   TUI/server/desktop all depend on.
3. **Integration tests**: real `SessionStore` + real tools + mock provider,
   exercising a full turn end to end, asserting the JSONL log is the ground truth
   and a resumed session reproduces the same event stream.
4. **TUI tests**: render Ink components to a string (`ink-testing-library`) —
   assert streaming, diff rendering, and permission-prompt output without a real
   terminal.
5. **Server tests**: boot `t3os serve` on an ephemeral port, drive a turn over
   WebSocket with the mock provider, assert the same `AgentEvent`s arrive (proves
   in-process and server paths are identical).
6. **Optional local-provider test**: one real small Gemma GGUF smoke test, gated
   behind an env flag / skipped in CI when the model isn't present.

### 6.3 Explicitly NOT auto-tested in v1

- Live HF API calls (mocked; a manual `t3os auth && t3os "hi"` smoke script is
  documented).
- The Tauri shell's native window (manual checklist).

### 6.4 Definition of done

The Section-1 success criteria, **each backed by a test**: TUI launches; point at
Gemma (HF token or local GGUF); edit a real file with visible diff; permission
prompt gates a write; sessions persist + resume; an external MCP server's tool
appears and runs; `t3os serve` boots and the shell talks to it.

## 8. Out of Scope / Future (v2+)

- **Full desktop GUI** built natively on Tauri (v1 ships only a thin shell).
- **Worktrees / multi-workspace parallel agent sessions.**
- **Remote-access service** and additional clients (mobile/web).
- Additional provider backends beyond HuggingFace + local.
